# 将来構想

## 概要

本ドキュメントでは、初期フェーズ（WireGuard + EC2の手動運用）以降に検討する拡張機能をまとめる。
優先度の高いものから順に記載する。

## Phase 2: 管理コンソール

### 目的

Admin管理者がWeb UIからVPNサーバーの起動/停止やユーザー管理を行えるようにする。

### 構成案

```
+------------------+     +-------------------+     +-----------------+
|  管理コンソール    |     |  管理API          |     |  VPN Server     |
|  (Frontend)      |---->|  (Backend)        |---->|  (EC2)          |
|  React / Next.js |     |  Lambda + API GW  |     |  WireGuard      |
+------------------+     +-------------------+     +-----------------+
                              |
                         +----+----+
                         | DynamoDB |
                         +----------+
```

### 機能一覧

| 機能 | 説明 |
|------|------|
| サーバー起動/停止 | ボタン1つでEC2の起動・停止 |
| ステータス表示 | EC2の状態、接続中のピア数 |
| ユーザー管理 | ピアの追加・削除・一覧 |
| QRコード表示 | 新規ユーザーのWireGuard設定QRコード |
| コスト表示 | 月間推定コストの表示 |

### 技術選定案

| コンポーネント | 候補 |
|--------------|------|
| Frontend | React + Next.js (静的エクスポート → S3 + CloudFront) |
| Backend API | AWS Lambda + API Gateway |
| データベース | DynamoDB (ユーザー情報、IP割り当て) |
| 認証 | Amazon Cognito |
| ホスティング | S3 + CloudFront (Frontend) |

### コスト影響

- Lambda + API Gateway: ほぼ無料（リクエスト数が少ないため）
- DynamoDB: 無料枠内で運用可能
- Cognito: 50,000 MAUまで無料
- S3 + CloudFront: 月額$1未満

## Phase 3: 認証・認可

### 目的

VPNの利用者を適切に管理し、不正利用を防止する。

### 認証フロー

```
1. Admin が管理コンソールでユーザーを登録
2. ユーザーにWireGuard設定（QRコード）を発行
3. ユーザーはiPhoneのWireGuardアプリで接続
4. Adminはいつでもユーザーのアクセスを無効化可能
```

### ユーザー管理モデル

| フィールド | 説明 |
|-----------|------|
| user_id | 一意のユーザーID |
| name | ユーザー名 |
| email | メールアドレス |
| public_key | WireGuard公開鍵 |
| assigned_ip | 割り当てIPアドレス |
| status | active / suspended / deleted |
| created_at | 登録日時 |
| last_connected | 最終接続日時 |

### 権限モデル

| ロール | 権限 |
|-------|------|
| admin | サーバー管理、ユーザー管理、全機能 |
| user | VPN接続のみ（管理コンソールへのアクセスなし） |

## Phase 4: 自動化・スケーリング

### 自動起動/停止

| 方式 | 説明 |
|------|------|
| スケジュール | EventBridge + Lambda で時間帯指定の自動起動/停止 |
| オンデマンド | API Gateway → Lambda → EC2起動のトリガー |
| 接続検知 | Route53ヘルスチェック + Lambda（高度） |

### スケーリング

現在の構成（EC2単体）では垂直スケーリング（インスタンスタイプ変更）が基本。

将来的な水平スケーリングが必要な場合：

```
Option A: 複数EC2 + Route53 加重ルーティング
  - 各EC2に異なるユーザーグループを割り当て
  - Route53でDNSベースの振り分け

Option B: ECS on EC2 (ホストネットワーク) + Auto Scaling
  - EC2 Auto Scaling Groupでインスタンスを増減
  - 各EC2上でWireGuardコンテナを実行
```

## Phase 5: 複数リージョン対応

### 目的

日本以外のリージョンからのアクセスも可能にする。
例: 米国のサービスに米国IPでアクセス。

### 構成案

```
                    +---> Tokyo (ap-northeast-1) ---> 日本のサービス
                    |
iPhone ---VPN---+---> US East (us-east-1) ---> 米国のサービス
                    |
                    +---> EU (eu-west-1) ---> 欧州のサービス
```

### 実装方針

- 各リージョンに同一構成のEC2をTerraformでデプロイ
- iPhoneのWireGuardアプリで複数トンネルを設定し、用途で切り替え
- 管理コンソールで全リージョンを一元管理

## Phase 6: IKEv2/IPSec追加対応

### 目的

WireGuardアプリをインストールできない環境向けのフォールバック。

### 追加作業

- strongSwanの構築・設定
- 証明書管理の自動化
- iOS標準VPN設定の.mobileconfigプロファイル生成
