# VPNプロトコル比較: WireGuard vs IKEv2/IPSec

## 概要

本ドキュメントでは、本プロジェクトで採用するVPNプロトコルとしてWireGuardとIKEv2/IPSecを多角的に比較し、推奨を決定する。

## 比較対象

| 項目 | WireGuard | IKEv2/IPSec |
|------|-----------|-------------|
| 登場年 | 2016年 (v1.0: 2020年) | 2005年 (RFC 4306) |
| コードベース | 約4,000行 | 数万〜数十万行 |
| Linux Kernel統合 | 5.6以降で標準搭載 | 対応済み |
| 設計思想 | シンプル・高速・モダン | 企業向け・柔軟・堅牢 |

## 詳細比較

### 1. 速度・パフォーマンス

#### WireGuard
- **スループット**: IPSecと比較して最大3〜4倍の速度
- **レイテンシ**: 接続確立が極めて高速（1-RTTハンドシェイク）
- **CPU負荷**: カーネル空間で動作し、最小限のオーバーヘッド
- **暗号処理**: ChaCha20Poly1305はモバイルデバイスで特に高速（ARM最適化あり）
- **接続復帰**: ローミング対応で、ネットワーク切り替え時にほぼ瞬時に再接続

#### IKEv2/IPSec
- **スループット**: WireGuardより劣るが十分な速度
- **レイテンシ**: IKE_SA_INIT + IKE_AUTH で2-RTT必要
- **CPU負荷**: ユーザー空間のデーモン + カーネル空間のIPSec処理
- **暗号処理**: AES-NI対応CPUでは高速だが、モバイルではChaCha20に劣る
- **接続復帰**: MOBIKE拡張でネットワーク切り替えに対応（WireGuardほど高速ではない）

**速度の勝者: WireGuard**

### 2. セキュリティ

#### WireGuard
- **暗号方式**: 固定（Noise Protocol Framework）
  - 鍵交換: Curve25519 (ECDH)
  - 暗号化: ChaCha20-Poly1305
  - ハッシュ: BLAKE2s
  - 鍵導出: HKDF
- **攻撃面**: コードが小さく監査が容易。暗号スイートのネゴシエーションがないためダウングレード攻撃不可
- **前方秘匿性 (PFS)**: 各ハンドシェイクで新しい一時鍵を生成
- **課題**: 暗号アルゴリズムに脆弱性が見つかった場合、バージョンアップが必要（暗号の交渉がないため）

#### IKEv2/IPSec
- **暗号方式**: 交渉可能（多数のスイートから選択）
  - 鍵交換: DH Group 14-21, ECDH
  - 暗号化: AES-128/256-GCM, AES-CBC, ChaCha20-Poly1305
  - 整合性: SHA-256/384/512, HMAC
- **攻撃面**: コードが大きく、設定の組み合わせが多いため攻撃面が広い
- **前方秘匿性 (PFS)**: Child SA再鍵で対応
- **課題**: 設定ミスにより弱い暗号スイートが使われるリスクがある

**セキュリティの勝者: WireGuard**（シンプルさによる安全性。ただしどちらも適切に設定すれば十分安全）

### 3. iPhoneクライアント対応

#### WireGuard
- **App Store**: 公式アプリ「WireGuard」が無料で提供
- **設定方法**:
  - 設定ファイル(.conf)のインポート
  - QRコードスキャン（最も手軽）
  - アプリ内で手動入力
- **On-Demand機能**: Wi-Fi/セルラーごとの自動接続ルール設定可能
- **制限**: App Storeからのインストールが必要

#### IKEv2/IPSec
- **iOS標準**: 設定アプリ > VPN から直接設定可能（アプリ不要）
- **設定方法**:
  - iOS設定画面で手動入力
  - .mobileconfigプロファイルの配布
- **On-Demand機能**: iOS標準のVPN On-Demand対応
- **制限**: 証明書ベース認証の場合、CA証明書のインストールが必要

**iPhoneクライアントの勝者: 引き分け**（WireGuardはQRコードが手軽、IKEv2はアプリ不要）

### 4. サーバー構築の複雑さ

#### WireGuard
- **インストール**: 1パッケージのインストールで完了
- **設定ファイル**: 10〜20行程度の簡潔な設定
- **鍵管理**: 公開鍵/秘密鍵のペアのみ（wg genkeyで生成）
- **ユーザー追加**: 設定ファイルに[Peer]セクションを追加するだけ
- **構築所要時間**: 15〜30分

```ini
# WireGuard サーバー設定例
[Interface]
PrivateKey = <server_private_key>
Address = 10.0.0.1/24
ListenPort = 51820
PostUp = iptables -A FORWARD -i wg0 -j ACCEPT; iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
PostDown = iptables -D FORWARD -i wg0 -j ACCEPT; iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE

[Peer]
PublicKey = <client_public_key>
AllowedIPs = 10.0.0.2/32
```

#### IKEv2/IPSec
- **インストール**: strongSwan等のインストール + 複数の設定ファイル
- **設定ファイル**: ipsec.conf, ipsec.secrets, strongswan.conf 等の複数ファイル
- **鍵管理**: CA証明書の構築、サーバー証明書、クライアント証明書の発行が必要
- **ユーザー追加**: 証明書発行 or ユーザー/パスワード追加 + 設定変更
- **構築所要時間**: 1〜3時間

```
# IKEv2/IPSec (strongSwan) 設定例
conn ikev2-vpn
    auto=add
    type=tunnel
    keyexchange=ikev2
    ike=aes256gcm16-sha384-ecp384!
    esp=aes256gcm16-sha384!
    dpdaction=clear
    dpddelay=300s
    rekey=no
    left=%any
    leftid=@vpn.example.com
    leftcert=server-cert.pem
    leftsendcert=always
    leftsubnet=0.0.0.0/0
    right=%any
    rightid=%any
    rightauth=eap-mschapv2
    rightsourceip=10.10.10.0/24
    rightdns=8.8.8.8,8.8.4.4
    eap_identity=%identity
```

**構築容易性の勝者: WireGuard**（圧倒的にシンプル）

### 5. 運用・メンテナンス性

#### WireGuard
- **ログ**: 最小限のログ出力（プライバシー保護の設計思想）
- **更新**: カーネルモジュールのため、カーネル更新で自動更新
- **監視**: `wg show` コマンドで接続状態を確認
- **トラブルシューティング**: シンプルなため原因特定が容易
- **再起動時**: systemdサービスとして自動起動設定可能

#### IKEv2/IPSec
- **ログ**: 詳細なログ出力が可能（デバッグに有利）
- **更新**: strongSwanパッケージの更新が必要
- **監視**: `ipsec statusall` で詳細な接続状態を確認
- **トラブルシューティング**: 設定が複雑なため原因特定に時間がかかることがある
- **再起動時**: systemdサービスとして自動起動設定可能

**運用性の勝者: WireGuard**

### 6. ユーザー管理のしやすさ

#### WireGuard
- 1ユーザー = 1つの[Peer]セクション（公開鍵 + 割当IP）
- ユーザー追加: 鍵ペア生成 → 設定ファイルに追加 → `wg syncconf`で反映（再起動不要）
- ユーザー削除: [Peer]セクション削除 → 反映
- **スクリプトで自動化が容易**

#### IKEv2/IPSec
- 証明書ベース: ユーザーごとに証明書発行が必要
- EAP認証: ユーザー名/パスワードをsecretファイルに追加
- ユーザー追加/削除時にサービス再起動が必要な場合がある
- **自動化は可能だが、WireGuardより複雑**

**ユーザー管理の勝者: WireGuard**

### セキュリティ監査・形式検証

WireGuardは**複数の形式検証および第三者監査**を受けている：

**形式検証 (Formal Verification)**:
- Tamarinによるシンボリック検証（鍵合意の正確性、前方秘密性、セッション一意性を証明）
- eCKモデルでの計算論的証明（Dowling & Paterson）
- CryptoVerifによるACCEモデル証明（メッセージ秘密性、相互認証、リプレイ攻撃耐性を証明）
- ProVerifによるシンボリック検証（Noise Explorer）
- Curve25519実装の検証（HACL* / Fiat-Crypto / Coq）

**第三者監査**:
- **Cure53**: WireGuardデーモンを監査 → 高いセキュリティ基準に適合と確認
- **Assured Security Consultants**: Rust実装を監査 → 軽微な問題2件のみ
- **Radically Open Security** (2023年): VPNサーバー（WireGuard含む）を監査
- **Linux Kernel v5.6への正式統合** (2020年): カーネルコミュニティによる広範なコードレビュー通過

### プライバシー

- App Store上の表記: **「Data Not Collected」**（データ収集なし）
- プライバシーポリシーで「ユーザー情報は一切開発元に送信されない」と明言

### iOS上での権限

| 権限 | 用途 | 必須 |
|------|------|------|
| Network Extension (Packet Tunnel) | VPNトンネル機能 | はい |
| VPN構成の変更 | VPN設定の追加（初回にiOSが確認ダイアログ表示） | はい |
| カメラ | QRコードスキャン | いいえ（オプション） |

iOSのサンドボックス内で動作し、他アプリのデータにはアクセスできない。

### 既知の脆弱性

| CVE | 内容 | WireGuard固有か |
|-----|------|----------------|
| CVE-2024-3661 | 「TunnelVision」DHCPオプション121でVPNバイパス | いいえ（VPN全般に共通） |
| CVE-2019-14899 | VPN接続の検出・仮想IP特定が可能 | いいえ（OS共通の問題） |

**WireGuardプロトコル自体の暗号実装に対する脆弱性報告はゼロ**。報告されているCVEはOS側のネットワークスタックやVPN一般に共通する問題のみ。

### 安全性の総合評価

**WireGuard iOSアプリは高い安全性と信頼性を持つ。** 根拠：

1. WireGuardプロジェクト**公式**アプリである
2. **完全オープンソース**（MITライセンス）で誰でもコードを検証可能
3. **5件以上の形式検証 + 複数の第三者監査**を通過
4. データ収集を**一切行わない**
5. Linuxカーネルに正式統合済み
6. プロトコル暗号実装のCVEが**ゼロ**
7. コードベースが約4,000行と小さく**監査が容易**

**留意点**: WireGuardプロトコルの設計上、接続中のクライアントIPがサーバー側に一時保持される。ただし本プロジェクトではサーバー運用者が自分自身であるため問題にならない。

## 決定事項

### メインプラン: WireGuard を採用

**理由:**

1. **速度**: 本プロジェクトで最も重要な要件。モバイルでの性能が特に優れている
2. **セキュリティ**: モダンな暗号のみを使用し、攻撃面が最小
3. **iOSアプリの安全性**: 公式・オープンソース・複数監査済み・データ収集なし
4. **構築・運用の容易性**: サーバー構築が圧倒的にシンプルで、ユーザー管理も容易
5. **スケーリング**: 設定ファイルベースのため、コンテナ環境との相性が良い
6. **iPhone対応**: App Storeの無料公式アプリで十分（QRコードで簡単設定）

### サブプラン: IKEv2/IPSec（将来追加の選択肢として保持）

IKEv2/IPSecは以下のケースに備えてサブプランとして残す：

- **WireGuardのUDPポート(51820)がブロックされる環境**でのフォールバック
- **WireGuardアプリをインストールできない端末**が必要になった場合（iOS標準機能で対応可能）
- **企業環境等で追加の認証方式**（証明書ベース、EAP）が求められる場合

WireGuardとIKEv2/IPSecは異なるポートを使用するため、同一サーバー上で両方を動作させることが技術的に可能。初期フェーズではWireGuardのみに集中し、需要に応じてIKEv2/IPSecを追加する。
